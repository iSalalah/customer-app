بوابة الخدمات الذاتية للمواطنين
ولوحة إدارة الطلبات للموظفين

مشروع يحمل اسم «بلدية ظفار» في المستودع، مخصص لاستقبال طلبات الخدمات البلدية عبر شاشات الخدمة الذاتية ومتابعتها داخل الجهة.

تاريخ إعداد الوثيقة: 5 سبتمبر 2026 · إصدار المشروع في package.json: 1.0.0 · الجمهور المستهدف: المبرمج أو الفريق المكلف بتقييم ملاءمة النظام للعمل.

التقدير الأولي: يحتوي المشروع على تطبيقات فعلية وكود خلفي وقاعدة بيانات واختبارات ووثائق تشغيل، مما يجعله أساسًا قابلًا للتقييم والتخصيص. صلاحية اعتماده تشغيليًا تتطلب تجربة مستقلة وربط الخدمات الخارجية والتحقق من متطلبات الجهة؛ وصفه في README بأنه جاهز للإنتاج لا يغني عن هذه الخطوات.

1. الغرض والقيمة العملية

يجمع النظام استقبال الطلبات ومرفقاتها وتوجيهها ومتابعة إجراءاتها في مكان واحد. يستطيع المواطن معرفة تقدم طلبه، ويستطيع الموظف معالجة الطلبات ضمن نطاق عمله، مع تسجيل الإسناد وتغييرات الحالة والملاحظات.

يمكن أن يفيد جهة تتعامل مع طلبات خدمات تُحال إلى دوائر وأقسام وموظفين. وتبقى مطابقة النماذج والموافقات والصلاحيات لإجراءات الجهة شرطًا لتحديد حجم التعديل المطلوب. تقليل المراجعات اليدوية وتحسين المتابعة فوائد متوقعة، ولم تُقَس في هذه المراجعة.

2. الوظائف الموجودة في المشروع

المكوّنالوظائف
واجهة المواطندخول برقم هاتف عُماني ورمز تحقق، استعراض الخدمات، تقديم طلب وإرفاق مستندات، عرض الطلبات الخاصة وتفاصيلها، والرد عند طلب معلومات إضافية.
شاشة الخدمة الذاتيةواجهة عربية وإنجليزية، دعم اتجاه العربية، لوحة مفاتيح افتراضية، إيصال قابل للطباعة عبر المتصفح ورمز QR للتتبع، وإنهاء الجلسة بعد عدم النشاط.
التتبع العاماستعلام برقم المرجع دون دخول، مع عرض حالة مختصرة. لا يميز التتبع العام بين القبول والرفض؛ كلاهما يظهر كطلب مغلق.
لوحة الموظفينقائمة طلبات وتفاصيلها، إسناد وإعادة إسناد بحسب الدور، تغيير الحالة، ملاحظات داخلية وردود مرئية للمواطن، وتنزيل المرفقات المسموح بها.
المؤشراتإجمالي الطلبات والمفتوح والمغلق، توزيع الحالات، متوسط زمن الإغلاق، أكثر الخدمات طلبًا، وتوزيع العمل بحسب نطاق المستخدم.
سجل الإجراءاتتسجيل إنشاء الطلب وتوجيهه وإسناده وتغيير حالته والملاحظات والردود والمرفقات، مع الفصل بين المحتوى الداخلي وما يراه المواطن.

3. المستخدمون والصلاحيات

المستخدمنطاق الوصول
زائراستعراض دليل الخدمات والتتبع العام المختصر.
مواطن مسجلطلباته ومرفقاته ومراسلاته المرئية له فقط.
موظفالطلبات المسندة إليه؛ لا يملك صلاحية الإسناد.
رئيس قسمطلبات قسمه وإسنادها إلى موظفين نشطين ضمن القسم.
مدير دائرةطلبات دائرته وإسنادها مع مراعاة تطابق قسم الموظف مع قسم الطلب عند وجود قسم للطلب.

تُفحص الصلاحيات في الخادم، ويُشتق توجيه الطلب من الخدمة المخزنة في قاعدة البيانات. لا تتضمن الأدوار الحالية دورًا عامًا لإدارة جميع الدوائر.

4. دورة الطلب

اختيار الخدمة ← التحقق من الهاتف ← تقديم الطلب والمرفقات ← التوجيه للدائرة والقسم ← الإسناد والمعالجة ← قرار نهائي

الحالات الداخلية: PENDING قيد الانتظار، IN_PROGRESS قيد المعالجة، NEED_INFO يحتاج معلومات، APPROVED مقبول، REJECTED مرفوض.

المسار أعلاه مثال تشغيلي مبسط؛ الانتقالات الفعلية محكومة بمصفوفة في الكود. يمكن طلب استكمال المعلومات أثناء المعالجة، ولا يمكن إعادة فتح الطلب بعد القبول أو الرفض في النسخة الحالية.

5. البنية والتقنيات

الطبقةالتقنية أو التنظيم الموجود
تنظيم المشروعمستودع واحد ومساحات عمل npm؛ JavaScript وJSX.
واجهات المستخدمReact 18، Vite 5، React Router، TanStack Query.
الخادمNode.js، Express 4، Zod للتحقق، Pino للسجلات. مجال Node المصرح به في package.json هو >=20.11 <23؛ يلزم تقييم تحديث الإصدارات ودعمها عند النشر.
البيانات والجلساتMySQL عبر Prisma 5؛ Redis للجلسات والعدادات وحدود الاستخدام. ملف Compose يستخدم MySQL 8.4 وRedis 7.4.
المرفقات والتكاملتخزين محلي أو متوافق مع S3، موصل رسائل SMS عبر HTTP، وموصل ClamAV لفحص الملفات.
التشغيل والتوثيقDocker Compose وnginx، ووصف OpenAPI مع Swagger UI، واختبارات Jest وSupertest.

المسارات الرئيسية: apps/api للخادم، apps/kiosk للمواطن، apps/admin للموظفين، packages/shared للقواعد المشتركة، وdocs للتوثيق. الكيانات الأساسية: الدوائر، الأقسام، الخدمات، الموظفون، المواطنون، الطلبات، المرفقات، الجلسات وسجلات الإجراءات والدخول.

6. ضوابط الحماية وحدودها

  • جلسات عبر ملفات تعريف ارتباط HttpOnly، وتخزين بصمات رموز الجلسة؛ يجب التحقق من إعداد Secure وHTTPS في بيئة النشر.
  • مهلة خمول المواطن الافتراضية دقيقتان، مع حد أقصى للجلسة ومسح حالة الواجهة عند انتهائها.
  • رموز تحقق قصيرة العمر وحدود للمحاولات والإرسال، وكلمات مرور الموظفين مشتقة باستخدام Argon2id مع قفل مؤقت بعد الإخفاقات المتكررة.
  • تحقق من الصلاحيات والملكية، وحماية CSRF وحدود استخدام، وفصل الملاحظات الداخلية عن استجابات المواطن.
  • المرفقات المسموحة PDF وJPEG وPNG؛ الحدود الافتراضية 10 ميغابايت للملف و5 ملفات للطلب، مع فحص النوع والمحتوى الثنائي.
  • إعداد الإنتاج يرفض مزود SMS الوهمي وتعطيل فحص الملفات وتفعيل مستكشف API. هذه فحوص إعداد، وليست شهادة بأن النشر الفعلي آمن.

7. ما يحتاج إلى استكمال أو تحقق

البندأثره على الاستفادة في العمل
SMS الحقيقييوجد موصل عام يحتاج مطابقة طلباته مع المزود المتعاقد معه، ثم اختبار التسليم والتأخير والفشل والتكلفة.
إدارة البيانات الأساسيةواجهات الموظفين الحالية تركز على الطلبات والمؤشرات؛ لا تظهر فيها شاشات لإدارة الموظفين أو الدوائر أو الخدمات. يلزم تحديد آلية الإدارة أو تطويرها.
هوية المواطنالدخول يعتمد على الهاتف. الرقم المدني لا تجمعه واجهة النسخة الحالية، ولا يظهر تكامل منفذ مع هوية حكومية.
حسابات الموظفينالمصادقة الثنائية غير مطبقة بحسب توثيق المشروع. يجب تحديد متطلبات الجهة لتسجيل الدخول وإدارة الحسابات.
متطلبات إضافيةالدفع الإلكتروني والتوقيع الرقمي والتكامل مع أنظمة الجهة ليست ضمن الوظائف المعروضة في هذه المراجعة؛ لا تُحتسب جاهزة دون فحص وتنفيذ محددين.
أجهزة الخدمة الذاتيةالطباعة من المتصفح؛ لا تكامل أصلي مع الطابعة. يلزم تجربة الشاشة والطابعة وطريقة إدخال المرفقات وضبط وضع Kiosk على الجهاز الحقيقي.
الإنتاج والاستمراريةملف Compose مخصص للتطوير والتقييم؛ يجب إعداد تمرير متغيرات SMS وS3 وClamAV، والشهادات والشبكة والنسخ الاحتياطي والمراقبة والاستعادة.
الحمل والأمانملف الحالة يذكر عدم إجراء اختبار حمل أو اختبار اختراق. القدرة الاستيعابية ومستوى الحماية يحتاجان قياسًا مستقلًا.

8. ما الذي تم التحقق منه عند إعداد هذا الملف؟

أُعدت الوثيقة بمراجعة README وملف حالة المشروع ووثائق المعمارية والصلاحيات والتشغيل، إضافة إلى ملفات الحزم ونموذج Prisma ومسارات لوحة الموظفين ودليل الخدمات وموصلات SMS وS3 وإعدادات البيئة وDocker. لم يُشغّل النظام أو تُعَد الاختبارات أثناء إعداد هذه الوثيقة، ولم تُجرَ مراجعة شاملة لجميع الشيفرة.

يسجل PROJECT_STATUS.md بتاريخ 5 سبتمبر 2026 نجاح 234 اختبارًا في 15 مجموعة، و37 فحص HTTP، وفحص lint، وتجارب متصفح، وعدم وجود ثغرات high أو critical في تدقيق الاعتماديات آنذاك. هذه نتائج منقولة من سجل المشروع وليست نتائج فحص جديد أو ضمانًا لحالة الاعتماديات اليوم.

9. خطة تقييم مقترحة للمبرمج

  1. التشغيل من نسخة نظيفة: تجهيز نسخة تجريبية وبيانات غير حقيقية، واتباع README ووثيقة النشر لإعداد البيئة والأسرار وMySQL وRedis والهجرات والبيانات التجريبية.
  2. التحقق الفني: تنفيذ npm run lint وnpm run build وnpm test وتدقيق الاعتماديات. إعداد TEST_DATABASE_URL وTEST_REDIS_URL لبيئة اختبار منفصلة والتأكد من عدم تخطي اختبارات التكامل.
  3. تجربة متكاملة: مواطن يقدم طلبًا بمرفق، مسؤول يسنده، موظف يطلب معلومات، المواطن يرد، ثم يُغلق الطلب ويُراجع سجل الإجراءات والمؤشرات.
  4. اختبارات حدود الوصول: منع مواطن من الاطلاع على طلب غيره، ومنع موظف من طلب خارج نطاقه، والتحقق من إخفاء الملاحظات الداخلية وانتهاء جلسة الشاشة العامة.
  5. ملاءمة العمل: مقارنة الخدمات والحقول والأدوار ومسارات الاعتماد والطباعة والتقارير باحتياجات الجهة وتوثيق الفجوات.
  6. التشغيل الفعلي: تجربة SMS وفحص المرفقات والنسخ والاستعادة، وقياس الأداء على الحمل المتوقع، ثم تشغيل تجريبي محدود قبل التوسع.

روابط التطوير الافتراضية بعد التشغيل: واجهة المواطن http://localhost:5173، لوحة الموظفين http://localhost:5174، ومستكشف API http://localhost:4000/api/docs.
